# ABWEICHUNGEN.md — Abweichungen vom BUILD-AUFTRAG (mit Begründung)

> Jede Abweichung wird hier protokolliert (harte Regel aus BUILD-AUFTRAG.md).
> Grundlagen-Konflikte (quellen/ gewinnt) sind ebenfalls hier festgehalten.

| # | Phase | Abweichung / Beobachtung | Begründung + Konsequenz |
|---|---|---|---|
| 1 | P0 | DLL-Methodenname `HoleAktuelleCOMPorts()` (COM großgeschrieben) statt `HoleAktuelleComPorts()` wie in wissen-programmierung.md §8 | Reflektions-Prüfung der Original-DLL (Quelle gewinnt): Signatur ist `string[] HoleAktuelleCOMPorts()`. Code verwendet die echte Schreibweise; wissen-Datei wird nicht angetastet (nicht verändertbar). |
| 2 | P1 | BUILD-AUFTRAG P1 nennt den eingefrorenen Vektor „AccessoryDesired=1.0 message“ mit den Bytes `… 00 00 80 BF` | Byte-Vektor ist bindend (VL5-Beispiel aus wissen §5). `00 00 80 BF` ist IEEE-754 **-1.0** (= Disarming-Beispiel der VL5-Folie). Test prüft die exakten Bytes unter dem korrekten Wertebild; der +1.0-Rahmen wird zusätzlich separat geprüft (`00 00 80 3F`). Keine Verhaltensänderung. |
| 3 | P0 | Core ist Multi-Target `netstandard2.0;net452` (statt nur netstandard2.0) | .NET Framework 4.5.2 kann KEINE netstandard2.0-Assembly laden (erst ab 4.6.1). Damit die WPF-Apps (eingefroren: net452) den Core überhaupt referenzieren können, liefert Core zusätzlich ein net452-Target. „Class library netstandard2.0, die auf Linux baut+testet“ bleibt erfüllt (Linux baut beide Targets via Reference-Assemblies-Paket; Tests laufen gegen netstandard2.0-Asset). Kein WPF-/DLL-Bezug im Core. |
| 4 | P0 | `.gitignore` zusätzlich um `.vorlage-ref/` und `libs/` erweitert | `.vorlage-ref/` = entpackte Vorlage (Referenz, nie committen). `libs/` enthält neben DLLs auch LED-PNGs als Kursmaterial — Leak-Scan-Regel (P6) verbietet Kurs-Binärdateien im (öffentlichen) Repo; `libs/` komplett zu ignorieren ist strikter und schützt vor versehentlichem `git add`. Beschaffung dokumentiert in `VORLAGE-DLLS.md`. |
| 5 | P0 | WPF-Apps referenzieren Core per `ProjectReference` mit `SetTargetFramework=TargetFramework=net452` | Notwendig, weil Core Multi-Target ist; sonst wäre dem old-style-csproj nicht eindeutig, welches Asset gemeint ist. Von VS2019 (MSBuild 16) unterstützt. |
| 6 | P0 | `SharpDX.XInput` als PackageReference im old-style csproj (kein packages.config) | VS2019 stellt PackageReference in non-SDK-Projekten vollständig bereit; moderne, von NuGet-Restore automatisch aufgelöste Form. Entspricht E8 (SharpDX.XInput via NuGet). |
| 7 | P2 | MainWindow.xaml beider Apps ist ein rein funktionales Platzhalter-Grid (kein visuelles Design, keine LED-Bilder) | Auftrag für Child A (Nightbuild-Aufteilung): P3/UI-Design macht ein anderer Agent. Vertrags-Elementnamen + Handler sind vollständig vorhanden; P3 kann direkt aufsetzen. |
| 8 | P2 | `IQuadroTransport` liegt im Core-Projekt, die Adapter in den Apps | BUILD-AUFTRAG fordert „Transport-Adapter (IQuadroTransport je App)“. Interface muss Core-seitig liegen, weil Core keine Kurs-DLLs referenzieren darf; so bleibt der Logikkern DLL-frei und testbar, während beide Apps ihre DLL kapseln. |
| 9 | P4 | Core-csproj enthält explizit `<ProjectGuid>` | Old-style-csproj-`ProjectReference` trägt die GUID; SDK-Projekte definieren standardmäßig keine. Explizite Angabe verhindert Auflösungsprobleme in VS2019. |
| 10 | P4 | Kleinschreibung der beiden Metadaten-Handshake-Strings bleibt erhalten (z. B. `3c 20 …`) | Wortwörtliche Übernahme aus VL5 (Vertragsforderung „never retype“). `SchickeHexString` parst Hex größenunabhängig; alle anderen erzeugten Nachrichten verwenden Großbuchstaben wie das VL5-Beispiel. |
